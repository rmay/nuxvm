# Port Quill to Fluxio

## Context

Quill (`apps/Quill.lux`, ~1000 lines) is the Plan9-style text editor for the NUX VM, written in Lux — the Forth-style concatenative language. The user keeps running into "rando issues" with it and wants to rewrite it in Fluxio, the newer C-like imperative language for the same VM (`docs/fluxio-language-plan.md`), which is structured and bounds-checked instead of relying on manual stack juggling.

This isn't a drop-in rewrite. Fluxio (v2e, current) is missing several things Quill depends on, and the two languages currently can't call into each other at all. Both compile to the same 55-opcode VM (`include/opcodes.h`), but each program is compiled as an independent flat blob loaded at a single base address (`vm_create`/`machine_create`, `src/machine.c:32`) — there is no linking step today, so a Fluxio program cannot reach a separately-compiled Lux binary's functions.

**Decision (per user direction): build a shared calling ABI between Lux and Fluxio, rather than reimplementing Quill's UI (menus/scrollbar/file-picker, currently `lib/ui.lux`/`lib/sf.lux`) from scratch in Fluxio.** This is more work up front but pays off beyond Quill — any future Fluxio app gets access to the existing Lux library ecosystem.

### Why the ABI is actually feasible

Both compilers already share the same VM-level calling convention: arguments are pushed on the data stack, `OP_CALL` transfers control, the callee's `OP_FRAME` pops `n` values into a dedicated `locals[]` region (`src/vm.c:526`, `v_0` = top-of-stack = local 0), and `OP_UNFRAME` restores the frame pointer without touching the data stack — so a value pushed before `UNFRAME` survives as a return value. This is VM-enforced, not per-compiler, so a Fluxio call and a Lux word call are binary-compatible in principle *if* argument push order lines up (verify before relying on it — see Phase B1).

What's actually missing is **addressing**, not convention: Fluxio needs a stable address to `CALL`, but Lux's compiler (`src/compiler.c`) assigns word addresses internally with no exported symbol table, and those addresses shift on every recompile. And nothing today loads two separately-compiled blobs into one VM's memory at once.

Address space check: Fluxio's graphical-target code loads at `GRAPHICAL_BASE_ADDRESS = 0x600000` (`include/vm.h:18`), and Quill's own large buffers (`FILE_BUF` etc.) start at `0x800000` (`apps/Quill.lux:46`). That leaves a 2MB gap comfortably free for a linked library image — no realistic compiled `.bin` gets close to that size.

## Phase 0 — Unified memory map (prerequisite, do this first)

Surveying every hand-picked global address across `apps/*.lux`/`lib/*.lux` turned up a real problem, not just a hypothetical one: **there is no address registry today.** Every module picks its own `0x8xxxxx`/`0x9xxxxx`/`0x5xxxxx`-ish block by hand, with zero coordination, and it's only harmless *because* each compiled program is currently the sole occupant of its own VM instance. Concrete collisions already exist in the repo:

- `lib/log.lux`'s `ENABLED-FLAG` (`0x803000`) sits inside `apps/Quill.lux`'s `FILE_BUF` span (`0x800000`–`0x900000`, `FILE_BUF_MAX = 0x100000`).
- `lib/mem.lux`'s `HEAP_START`/`HEAP_END` (`0xA00000`–`0xC00000`) overlaps `apps/Quill.lux`'s `PASTE_BUF` (`0xA00000`, 64KB).
- `lib/mem.lux`'s `HERE_ADDR` (`0x8E0000`) collides with `lib/ui.lux`'s entire component-state block, which also starts at `0x8E0000`.

These are landmines waiting for the day two of these modules get included together — which is exactly what Phase B's linking work does on purpose (putting an independently-authored Lux library and a Fluxio app in one VM's address space at once). This needs fixing before the ABI work, not after.

**Deliverables:**

1. **`include/memory_map.h`** — one authoritative header, included by `luxc`, `fluxioc`, `fluxlink`, and the VM itself, naming every reserved band: device space (existing `DEVICE_MEMORY_OFFSET`/`DEVICE_MEMORY_SIZE`), headless code (`HEADLESS_BASE_ADDRESS`), graphical code (`GRAPHICAL_BASE_ADDRESS`), Fluxio's small-scalar globals band (existing `FX_GLOBALS_BASE`/`FX_DEVICE_BOUNDARY`, ~60KB), a **new** Fluxio bulk-array globals band (large `byte[]`/`int[]` globals — Quill's file buffer alone needs 1MB, which doesn't fit the existing low-RAM budget), the Phase B3 ABI library-link band, and an app-bulk-buffer band for hand-authored large Lux buffers (font data, paste/heap buffers, etc.) that replaces "whichever `0x8`- or `0x9`-prefixed address looked free."
2. **Fix the three concrete collisions above** by moving the offending constants into the new bands, and land `docs/memory-map.md` (generated or hand-maintained from the header) as the living reference — replacing tribal knowledge of "which block is whose."
3. **A best-effort `luxc` collision check.** Lux still requires hand-authored addresses (a full compiler-managed allocator for Lux is a larger, separate change, out of scope here); the cheapest real win is flagging duplicate base addresses across a program's transitive includes at compile time. Catching sub-range overlaps (like the `log.lux`/`FILE_BUF` case) would need per-constant size annotations Lux doesn't have today — don't build that unless duplicate-base detection turns out to be insufficient in practice.
4. **Extend Fluxio's globals allocator** (`next_addr`/`FX_GLOBALS_BASE`/`FX_DEVICE_BOUNDARY` in `src/fluxio_codegen.c`) with a second bump allocator for large arrays, placed in the new bulk-globals band. This is also a hard prerequisite for Phase A1 (`byte file_buf[1048576];` doesn't fit the current 60KB budget) — so Phase A1 depends on this shipping first.
5. **`luxc` gains a `-base 0xADDR` override** (today only the two fixed target constants exist), so a Lux "library build" (Phase B) can target the new ABI library-link band instead of colliding with `GRAPHICAL_BASE_ADDRESS` — which today implicitly means "whichever program is the sole occupant of the VM," an assumption the linking work breaks on purpose.

This phase directly unblocks Phase B (the library-link band and `-base` override are exactly what `fluxlink` needs) and Phase A1 (the bulk-globals band). Do Phase 0 before A/B/C.

## Phase 0.5 — ABI stability contract

The user's explicit requirement: the Lux↔Fluxio ABI must not be a moving target — it should be something **any** compiler can build against, with guarantees enforced by tooling, not just documented as a convention people are expected to honor. Four concrete mechanisms, each backed by something that fails a build rather than relying on discipline:

1. **A machine-readable spec, not just prose — done, see `abi/nux-abi.json`.** Defines the calling convention (stack-arg order, `FRAME`/`UNFRAME` semantics — already fixed by the VM's 55 opcodes, so this is transcribing an existing invariant, not inventing one, and empirically verified by `src/test_abi_conformance.c`), the Phase 0 memory-map bands, the linked-image layout (magic number + version word + trampoline table, corrected to the merged-single-blob format — see Phase B4), and the append-only policy below. A linker checks this before linking and refuses on mismatch, instead of silently producing a corrupt image.
2. **Append-only trampoline tables, enforced by the linker.** Each library ships a committed symbol table file (e.g. `lib/ui.symtab.json`, produced by Phase B2's `luxc -symbols` and checked into the repo). `fluxlink` (Phase B3) diffs a fresh compile's symbol table against the committed one and **errors** if any existing slot is reordered, renamed, or removed — new exports may only be appended at the end. This is what actually keeps old compiled Fluxio binaries working against a newer library build; the trampoline stub's slot order is the entire compatibility surface, so this is the single most load-bearing check in the whole ABI. (Not yet implemented — depends on B2/B3 existing first.)
3. **A conformance test suite, not compiler-specific trust — done, see `src/test_abi_conformance.c`, run via `make test`.** Currently covers: 0-arg call with a return value, multi-arg call verified for push-order correctness (not just "a plausible-looking result"), and a merged single-image blob spanning the real code↔library-link address gap. Struct-by-reference argument passing (matching what Quill's UI calls need) is still to be added once Phase B5's `extern` declarations exist to model it against. Any compiler targeting this ABI — Lux, Fluxio, or a future third one — proves compliance by passing this suite, not by re-reading this document and hoping.
4. **Version bumps are new address ranges, never overwrites.** If an incompatible change is ever unavoidable, it gets a new library-link band and a new magic version (Phase 0's `memory_map.h` reserves room for this); the old version's linked libraries keep working at their frozen addresses indefinitely — the same discipline as never reusing a syscall number.

This phase's output (the versioned header format and the symtab-diff rule) is a direct input to Phase B3's `fluxlink` design — the smoke test in point 3 already caught and fixed a real design bug in the original Phase B4 (see below) before any linker code was written.

## Phase A — Fluxio language/runtime extensions

Independent of the ABI work; Quill's core editing logic (text buffer, file I/O, rendering) still needs to be written in Fluxio itself. Work happens in `include/fluxio_ast.h`, `src/fluxio_parser.c`, `src/fluxio_codegen.c`, `src/fluxio_lexer.c`, with new cases added to `src/test_fluxio_compiler.c` for each addition.

**A1. `byte` array type — done.** New element type alongside `int[]`: `byte name[N]` for globals, locals, and array parameters (`include/fluxio_token.h`'s `FXTOK_KW_BYTE`, `src/fluxio_parser.c`, `src/fluxio_codegen.c`), bounds-checked `[]` via the existing `emit_bounds_check`. Only legal in array form — `byte x;` and `byte x` as a scalar param are both rejected at parse time ("'byte' may only be used as an array...").
&nbsp;&nbsp;&nbsp;&nbsp;**Design finding while implementing:** "1 byte per slot" only applies to *global* byte arrays. A local array has no real memory address at all — it lives in the VM's frame-relative `locals[]` region, addressed only via `OP_LOCALGET`/`OP_LOCALSET` slot numbers (already word-sized, one per slot, with no sub-word addressing the VM exposes) — so a local `byte[]` costs exactly the same codegen as a local `int[]` (`FxNode.local_decl.is_byte` is carried for documentation/future use but changes nothing at codegen time). The real packing win — and the reason this phase exists at all, since it's what makes Quill's 1MB file buffer affordable — is *global* byte arrays: `FxGlobal.is_byte` routes global allocation to 1 byte/element instead of 4 (`src/fluxio_codegen.c`'s global-allocation loop and string-literal-init codegen, both updated), and indexed access on a global (or a byte-array parameter, which decays to the same real address) uses the existing compiler-internal `emit_load_byte`/`emit_store_byte` with 1-byte index stride instead of `OP_LOADI`/`OP_STOREI` with a `*4` stride (`FxBinding.is_byte`, threaded through `FX_INDEX`/`FX_INDEX_ASSIGN` codegen).
&nbsp;&nbsp;&nbsp;&nbsp;Verified: `byte file_buf[1048576];` (matching Lux's 1MB `FILE_BUF_MAX`) round-trips correctly through the bulk-globals band from Phase 0; a byte array passed as a function parameter indexes with the correct 1-byte stride inside the callee (the actual failure mode this design was checking for — a word-stride bug here would silently read/write the wrong bytes, not fault). Both covered by permanent tests, `test_byte_arrays`/`test_error_byte_type_misuse` in `src/test_fluxio_compiler.c`.

**A2. File VFS builtins — done**, extending `FX_BUILTINS` in `src/fluxio_codegen.c` (protocol ground truth: `src/system.c` `handle_sci`'s `SCI_VFS_*` cases):
- `vfs_open_buf(path_buf, path_len, flags) -> fd` — runtime buffer+length (not just a literal, unlike the existing `vfs_open(literal)`), so a path picked at runtime (file picker, default filename) can be opened for read or write. Named distinctly from `vfs_open` rather than overloading it — Fluxio builtins have one fixed arg spec per name, and `vfs_open`'s existing string-literal-only callers (`examples/fluxio/*.fx`, existing tests) shouldn't need to change. `SCI_VFS_OPEN` itself has no length parameter — it reads a NUL-terminated C string — so this builtin NUL-terminates at `path_buf[path_len]` itself before issuing the syscall (caller must reserve `path_len + 1` bytes).
- `vfs_read(fd, buf, maxlen) -> bytes_read`
- `vfs_write(fd, buf, len) -> bytes_written`
- `vfs_seek(fd, pos) -> result`
- `vfs_stat(fd) -> size`
- `vfs_write_chunk(fd, buf, len, offset, orig_len) -> result` — packs the 5-word param block `SCI_VFS_WRITE_CHUNK` expects (`src/system.c`), same as `VFS::write-chunk` (`lib/vfs.lux`) does today. Note: `system.c`'s current handler only consumes `fd`/`buf`/`len` from that block (`offset`/`orig_len` are packed but not yet read on the C side) — a pre-existing gap in the underlying protocol, not something this phase introduced or needed to fix, since `write_bytes`/`offset`/`orig_len` still round-trip correctly for the whole-buffer-write case Quill needs.

Verified end-to-end against real host-backed files under `/sys/file/` (not just a fault-free-run smoke test): write+read round-trip, seek-then-partial-read, and stat, all with byte-array buffers from Phase A1. Permanent tests: `test_vfs_write_read_roundtrip`/`test_vfs_seek_and_stat`/`test_vfs_write_chunk` in `src/test_fluxio_compiler.c`.

**A3. Runtime-length text drawing — done.** New builtin `draw_bytes(fd, x, y, color, scale, buf, len)` alongside the existing literal-only `draw_str`, so Quill can draw live file/line content instead of only compile-time strings. Same `FX_DRAW_CMD_DRAW_STRING` wire packing as `draw_str`, but since the text isn't known at compile time, `draw_str`'s compile-time-unrolled byte packing doesn't apply — this emits a real runtime copy loop instead (bounded to the fixed `sci_buf_addr` scratch region's capacity). `len` is clamped to `[0, capacity]` at runtime before the copy (and before the packed wire-format length field is written) — an oversized or negative caller-supplied `len` is capped/floored rather than overrunning `sci_buf_addr` into adjacent reserved scratch (mouse/kbd event buffers, etc.) or underflowing into a huge copy. Verified two ways: pixel-exact equivalence against `draw_str` rendering the same text (not just "didn't fault"), and an oversized-`len` case confirming the clamp holds. Permanent tests: `test_draw_bytes_matches_draw_str`/`test_draw_bytes_oversized_len_clamped` in `src/test_fluxio_compiler.c`.

**A4. No new builtin needed for memmove.** Once A1 lands, Quill's insert/delete byte-shifting (today's `MEMORY::move-mem`) is just an ordinary Fluxio function looping over `byte[]` indices — bounds-checked for free.

## Phase B — Shared Lux/Fluxio calling ABI

**B1. Calling-convention smoke test — done, see `src/test_abi_conformance.c`.** A permanent test (not a one-off manual check) that hand-builds bytecode standing in for what Fluxio's `extern`-call codegen will eventually emit, and calls real `luxc -base`-compiled Lux words through it. Confirms: (1) left-to-right argument push order matches Lux's Forth `( a b -- )` convention exactly (`sub(10, 3) == 7`, an order-sensitive check, not `add` which would pass even with args swapped); (2) a merged single-image blob spanning the real `MM_GRAPHICAL_CODE_BASE`→`MM_ABI_LIBRARY_LINK_BASE` gap runs correctly (see B4 below — this is also what caught the B4 design correction). Run via `make test`.

**B2. Symbol export from `luxc`.** Extend `src/compiler.c`/`src/luxc.c` with an export mode (e.g. `-symbols out.symtab` alongside `-o out.bin`) that dumps exported word name → final byte address once compilation finishes assigning addresses.

**B3. New `fluxlink` tool** (`src/fluxlink.c` → `bin/fluxlink`, added to `Makefile`). Takes a compiled Lux library `.bin`, its symbol table, and a declared ordered list of exported entry points; emits a small fixed-layout **trampoline stub** (magic + version header per Phase 0.5, then one 5-byte `JMP <real target>` per exported symbol, in a stable declared order) at a reserved fixed base address, followed by the library's own code/data. Proposed base: `0x700000` (between Fluxio's own code region at `0x600000` and Quill's buffer region at `0x800000`). The trampoline indirection is what keeps Fluxio's `extern` addresses stable across library recompiles — only the stub's slot order matters, not the library's internal layout — and `fluxlink` enforces that order via the Phase 0.5 append-only symtab-diff check, not just by convention.

**B4. Merged single-image linking (revised — no VM/loader change needed).** Originally scoped as a "dual-image loader" change to `cloister.c`/`vm_create`. **Corrected during the Phase B1 smoke test** (`src/test_abi_conformance.c`, `test_dual_image_single_blob`): the VM restricts PC execution to one contiguous `[image_base, image_end)` window (`vm_create` sets `image_end = base_address + program_size`; execution outside it faults "execute outside program", `src/vm.c` ~line 266) — so a linked library can't be a second, independently-loaded VM image at all. `fluxlink` must instead emit **one merged blob**: the app's own bytes, a zero-padded gap, then the linked library's bytes (magic/version header + trampoline table + code), all in a single buffer spanning from the app's base address through the library's end. That merged blob loads exactly the way any standalone `.bin` already does today — confirmed by the smoke test, which built and ran exactly this shape spanning the real `MM_GRAPHICAL_CODE_BASE`→`MM_ABI_LIBRARY_LINK_BASE` gap (`0x600000`→`0x700000`) without any `cloister.c`/`vm.c` changes. This simplifies B3 (which now owns producing the merged blob directly) and removes B4 as a separate implementation item.

**B5. Fluxio `extern` declarations — done, see `include/fluxio_token.h`/`src/fluxio_parser.c`/`src/fluxio_codegen.c`.** New declaration form binding a name + arity to a fixed trampoline address, e.g. `extern int ui_menubar(int w);`, callable via ordinary `OP_CALL` codegen. Extended with an `extern void f(...)` variant (see B6 below) once B6 exposed a real gap in the original one-form design.

**B6. Adapt `lib/ui.lux`/`lib/sf.lux` callback entry points to polling — done.** `lib/ui.lux` already had a `post`/`poll` name-keyed event queue (used internally by every widget, including menu items — `UI::item`'s `handler` param is only invoked if non-zero, so Fluxio can already pass literal `0` and skip registering a callback entirely). What was missing was a *fixed-arity* way for Fluxio to drain it: `poll` itself returns `0` or `name ev val 1` (variable stack depth), which doesn't fit `extern`'s one-fixed-signature model. Added `UI::poll-next ( -- ready? )` / `poll-name` / `poll-ev` / `poll-val` — `poll-next` stores the popped event into three globals (`UI_POLL_NAME/EV/VAL`, `0x8E0F78`+) and returns just the ready flag; the three getters read them back one at a time. `lib/sf.lux`'s `on-ok!`/`on-cancel!` quotations similarly can't be supplied by Fluxio, so `SF::picked?`/`SF::cancelled?`/`SF::clear-result!` flags were added, set unconditionally in `choose-file`/`cancel` alongside the existing (still-working, for Lux callers) callback dispatch. All additive; existing Lux apps unaffected (`make apps` recompiles clean, `make test` green).
&nbsp;&nbsp;&nbsp;&nbsp;**Design gap this surfaced, fixed before B7:** Fluxio's `FX_EXPR_STMT` codegen unconditionally emits `OP_POP` after any statement-context call, since ordinary Fluxio functions and the B5 `extern int` form always leave exactly one return value. Most of the UI/SF words worth exporting are `( ... -- )` — they push nothing. Calling one through the original single `extern` form would have silently popped whatever the *next* instruction produced instead of faulting — a real stack-corruption bug, not hypothetical (the plan's own B7 list is majority void words). Fixed by adding `extern void f(...)` as a distinct declared form (`FxExtern.is_void`): codegen skips the trailing `OP_POP` for a void call used as a statement, and using a void extern's result as a value is now a compile-time error instead of reading garbage. Proven by a permanent regression test, `test_fluxio_extern_void_end_to_end` (`src/test_abi_conformance.c`): two consecutive void calls followed by a value-returning call, checked for a stack-correct result. `abi/nux-abi.json`'s `calling_convention.return_value` documents the void/non-void distinction as part of the ABI contract, not just a Fluxio-side implementation detail.

**B7. Compile and link the UI library — done.** `lib/sf.lux` (which transitively includes `lib/ui.lux`) compiles as one library via `make uilib` (`luxc -base 0x701000 -symbols lib/uisf.symtab.json -o lib/uisf.bin lib/sf.lux`; both artifacts gitignored like every other `*.bin`/build output). The committed, append-only export contract is `abi/uisf.exports.json` — 21 `UI::` words (`new`, `menubar`, `menu`, `item`, `check-item`, `sep`, `sbar-init/draw/press/drag/release/set-val`, `feed`, `draw`, `handle`, `menu-open?`, the new `poll-next/name/ev/val`, `in-rect?`) and 10 `SF::` words (`show`, `hide`, `open?`, `path`, `mouse`, `kbd`, `draw`, the new `picked?`/`cancelled?`/`clear-result!`), each marked void or int per B6's finding — Phase C's `apps/Quill.fx` `extern` declarations must match this void/int split exactly. Proven end-to-end by a permanent test, `test_uisf_library_link` (`src/test_abi_conformance.c`): compiles the real `lib/sf.lux`, links it against a placeholder Fluxio app via `fluxlink` using the real committed `abi/uisf.exports.json`, and calls `UI::new` (void) then `UI::menu-open?` (int) through real trampoline slots, checking the library's internal state was actually initialized (`menu-open?` reads back `0`).

## Phase C — Port Quill's editing logic

Translate `apps/Quill.lux`'s algorithms into Fluxio functions using Phase A's byte buffers/VFS/draw builtins, calling into the linked UI library from Phase B for menus/scrollbar/file-picker:

- Line cache (`rebuild-lines`), coordinate mapping (`rc-from-idx`/`idx-from-rc`/`click-idx`) — same algorithm, `byte[]` indexing instead of `load-byte`.
- Lazy chunked load/save (`load-chunk-at`/`save-current-chunk`/`check-lazy-load`) via `vfs_seek`/`vfs_read`/`vfs_write_chunk`.
- Insert/delete/selection (`insert-char`/`insert-bytes`/`delete-char`/`delete-selection`), memmove written as a plain Fluxio function (A4).
- Hex mode rendering and toggling.
- Save/snarf/paste (`/sys/snarf` open/read/write).
- Menus, scrollbar, file picker: calls through the B5 `extern` bindings into the linked `ui.bin`/`sf.bin`, polling the B6 state instead of registering callbacks.
- Event dispatch: a single top-level loop (`while (1) { begin_frame(); poll_mouse(...); ...; poll_kbd(...); ...; end_frame(); yield(); }`) replacing `APP::on-mouse!`/`on-kbd!`/`on-frame!`/`on-resume!` registration — Quill's dispatch is already flag-driven (`SF::open?`, `UI::menu-open?` checks), so this mostly inlines what's already effectively procedural.

**Recommended build order**: prove Phase B's ABI end-to-end on something trivial first (call one real `lib/ui.lux` word — e.g. draw a filled rect via a Lux wrapper — from a minimal Fluxio program) before porting Quill's UI usage wholesale. Then get a minimal Quill loop working (open default file into a `byte[]` buffer, `draw_bytes` it, move cursor, type/backspace, save) before layering hex mode, selection, scrollbar, and the file picker on top.

**Status: minimal loop (v1) + word-wrap/mouse-selection (v2) + hex view (v3) + linked scrollbar (v4) + status bar (v5) + viewport auto-follow (v6) + menu bar (v7) + menu bar in hex mode (v8) + hex-mode scrolling/click-to-position (v9) + hex-mode nibble editing, ASCII-following caret, and a live hex-mode menu checkbox (v10), hollow blue hex-mode caret styling (v10.1) + hex-mode Up/Down row movement (v10.2) + a real File > Open... file picker (v11) + File > Save As via `SF::show-save` (v13) done, see `apps/fluxio/Quill.fx`.** Open/display/cursor-move/insert/delete/save all work end-to-end against a real host file, driven by genuine simulated-input tests (not just "compiles and doesn't fault") in `src/test_fluxio_compiler.c`:
- `test_quill_fx_type_and_save` — binds a channel to `/dev/kbd`, injects real keydown packets to type "Hi", saves, quits, then re-opens the saved file through a *separate* `System` to confirm the on-disk bytes are exactly right.
- `test_quill_fx_click_positions_cursor` — seeds a real 3-line file, injects a `/dev/mouse` MOUSE_DOWN packet at a specific pixel position, types a character, and confirms the saved bytes land exactly where that click should have placed the cursor (proves the y→line and x→column mapping in `find_click_index`/`rebuild_lines`, not just "it renders").
- `test_quill_fx_wraps_long_word_without_fault` — a 300-byte line with no spaces (the "no space to wrap at" edge case that risks an infinite loop in a from-scratch line-wrap implementation), run for many frames, then edited and saved to confirm the buffer wasn't corrupted by the forced hard-wrap.
- `test_quill_fx_hex_mode_toggle` — toggles into hex mode (Home), renders it for several frames, moves the cursor with arrow keys while in hex mode, toggles back to text mode, types a character, and confirms it lands at the byte offset the hex-mode cursor movement should have left it at — proves the toggle doesn't lose or corrupt cursor/buffer state, not just "the hex view doesn't crash".
- `test_quill_fx_scrollbar_scrolls_view` — the first Quill.fx test that exercises the *linked* UI library rather than pure self-contained Fluxio: seeds 200 lines (far more than the default 640×480 canvas's ~22 visible rows), pages the real `UI::sbar-press`-backed scrollbar down via three track clicks, then clicks near the top of the text pane and types a marker character. The saved marker lands deep in the file, not at line 0 — proving the scrollbar's value, `find_click_index`, and `draw_buffer` are all reading the same scroll offset, not just that the bar renders.
- `test_quill_fx_status_line_reflects_dirty_state` — edits one character (setting `dirty`) and confirms the status bar's total ink-pixel count over its whole text band increases (the " *" marker appearing), then saves (clearing `dirty`) and confirms it drops back down. Caught a real test-authoring bug during development: an earlier single-row version of the ink-count helper sampled a row where the before/after glyph difference happened not to register, even though the marker was genuinely being drawn and other rows clearly showed the change — fixed by summing ink across the whole status-bar band instead of one row, a good reminder that a pixel probe needs to cover where a real difference could land, not just one plausible-looking sample point.
- `test_quill_fx_viewport_follows_cursor` — clicks below all on-screen lines to jump the cursor to end-of-buffer without ever touching the scrollbar, then clicks near the top of the pane again and confirms it lands on whatever line the auto-follow brought into view, not line 0.
- `test_quill_fx_menu_bar_renders` — a pixel-presence check (ink count over the menu bar's row band > 0), added after the menu bar was found to fire correctly but not actually paint anything (see the v7 bug note below) — proves what the functional click tests below can't.

&nbsp;&nbsp;&nbsp;&nbsp;**Design correction caught by testing before it shipped:** the first version called `ensure_cursor_visible()` unconditionally every frame, right before drawing. v9 bug report from actual use: a screenshot showed a file whose last hex row has fewer than 16 bytes (e.g. an 11-byte final row) with its ASCII column visibly out of line with the ASCII column in the full rows above it — not the expected extra blank space where the missing bytes would be, but the column itself landing at the wrong x. Root cause: `draw_hex_buffer` drew each hex row as a single `draw_bytes` call over the whole 72-byte `hex_line_buf`, and `render_hex_row` used to fill a short row's unused hex-pair slots with literal space characters. In Quill.fx's proportional font, a run of blank spaces doesn't accumulate the same pixel width as a run of real two-digit hex pairs would, so the buffer's fixed ASCII-column *character index* (56) ended up at a different accumulated pixel *x* for a short row than for a full one — confirmed by direct pixel measurement: full rows' ASCII column started ~46–50px to the right of the short row's.
&nbsp;&nbsp;&nbsp;&nbsp;First fix attempt (reverted): anchor the ASCII draw to a separate canonical, content-independent formula that always assumed a full 16 pairs of width, splitting the row into two `draw_bytes` calls. Measuring it against real rendered rows showed it *increased* the gap rather than closing it — the canonical formula didn't reflect the font's real advances closely enough. Reverted in favor of the simpler fix the user actually suggested: have `render_hex_row` always render all 16 hex-pair columns, treating a column past end-of-file as a phantom zero byte (`00`) instead of leaving it blank — the same convention `hex_col_x` (used for the caret) already uses for out-of-range columns, so the two functions are now consistent with each other instead of using two different models. Every row now accumulates real-digit width the whole way to the ASCII column regardless of how many bytes it actually has, and `draw_hex_buffer` goes back to a single `draw_bytes` call per row. A `00`-filled tail past end-of-file reads as `.` in the ASCII column, same as any other non-printable byte — no new ambiguity beyond what the hex view already has for control characters. Verified by a new test, `test_quill_fx_hex_ascii_column_aligns_on_short_row`: seeds the same row shape as the reported screenshot (two full rows + an 11-byte last row) and confirms all three rows' ASCII columns land within a few pixels of each other (the same small row-to-row jitter full rows already show one another, from real digit glyphs of different values measuring slightly differently) — confirmed the test fails against the pre-fix blank-fill code (a 50px+ miss, far outside that tolerance) before trusting it.

v10 addition — **hex-mode nibble editing, an ASCII-following caret, and a live hex-mode menu checkbox**, three related requests in one pass: "set a check on the menu" for the current mode, "cursor in hex should have one in ascii that follows along", and "allow editing the hex". None of this had a reference to port from — checked `apps/Quill.lux` directly and it turns out the original doesn't implement hex-mode byte editing either (its own `menu-cut`/`paste-snarf` explicitly no-op in hex mode) despite the header comment here previously claiming otherwise; this is new functionality, not parity work.
&nbsp;&nbsp;&nbsp;&nbsp;**Nibble editing**: a new `hex_nibble` global (0 = high nibble, 1 = low) tracks which half of the byte under `cursor` is being typed into; it resets to 0 whenever the cursor moves by any other means (arrow keys, a click, or a mode toggle), so a stale nibble selection can never survive a jump to a different byte. `hex_digit_value(key)` maps `'0'-'9'`/`'A'-'F'`/`'a'-'f'` to 0-15 (anything else returns -1 and falls through untouched). `edit_hex_nibble(digit)` writes the nibble into `file_buf[cursor]` via a mask-and-OR, then either advances `hex_nibble` to the low half (after the high nibble) or wraps back to 0 and advances `cursor` to the next byte (after the low nibble, the usual "two keystrokes per byte" hex-editor rhythm) — capped at not stepping past `file_len` (this doesn't insert/extend the file, only overwrites existing bytes). `rebuild_lines()` runs after every edit so the word-wrap cache doesn't go stale for whenever the user flips back to text mode. Verified by `test_quill_fx_hex_nibble_edit`.
&nbsp;&nbsp;&nbsp;&nbsp;**ASCII-following caret**: `draw_hex_buffer` now draws a second caret in the ASCII column, on the same row, at the column corresponding to the hex caret's byte — so it's visible at a glance which ASCII character the byte under the hex cursor decodes to. The primary hex caret itself also became nibble-aware: it now shifts right by the high nibble's glyph width when `hex_nibble == 1`, so it visibly tracks which half of the byte is selected, not just which byte. Verified empirically (not by a permanent test — this is a purely visual aid with no behavioral consequence a save/load round-trip would catch): direct pixel inspection confirmed a caret in both the hex-pair region and the ASCII column, both shifting right together as the cursor advances.
&nbsp;&nbsp;&nbsp;&nbsp;**Live hex-mode menu checkbox**: `ui_item(menu_hex_label, 0)` became `ui_check_item(menu_hex_label, 0)` (`UI::check-item` was already exported at index 4, just unused until now) so View > Toggle Hex renders with a checkmark. `lib/ui.lux`'s own `mb-apply` auto-toggles a check-item's internal `MI_CHK` state on click, which would be enough on its own *if* the menu were the only way to flip `hex_mode` — but `toggle_hex_mode()` is also called from the Home-key shortcut, which never touches menu state at all, so relying on the auto-toggle alone would let the checkbox and the real mode drift out of sync the first time someone used Home instead of the menu. Fixed by exporting `UI::item-set` (`abi/uisf.exports.json`, index 32 — append-only, `(name val --)`, finds a menu item by its text pointer and sets its checked state directly) and calling it from `toggle_hex_mode()` itself, unconditionally, on every toggle regardless of what triggered it. Verified by `test_quill_fx_hex_menu_checkbox_syncs_via_home_key`: toggles via the Home key only, then opens the dropdown and confirms the checkmark's ink is present — specifically exercising the path a menu-click-only test wouldn't catch.

v11 addition — **the file picker**, the last of the three deferred "smaller gaps vs. the file picker" items and the reason `abi/uisf.exports.json`'s `SF::*` entries existed at all before now (Phase B7). File > Open... calls `SF::show`; while `SF::open?` is true, every mouse and keyboard event goes to `SF::mouse`/`SF::kbd` instead of Quill's own click/key handling — same "modal owns all input" precedence the menu bar already established for itself, just one tier further in. `SF::draw` is called last, after `UI::draw`, so the dialog paints on top of everything. Two real integration gaps had to be closed to make this work at all, both because Quill.fx bypasses `APP::init`/`APP::loop` entirely (it's a self-contained event loop, not an `APP`-framework app):
&nbsp;&nbsp;&nbsp;&nbsp;**Reading the picked path.** `SF::path` returns a raw Lux C-string pointer, and Fluxio has no builtin to peek an arbitrary byte at a runtime address or strlen a foreign pointer — Phase A1/A2's `byte[]` support only covers Fluxio's own declared arrays. Fixed by adding `SF::path-copy (dest max -- len)` to `lib/sf.lux` (append-only export, index 33): it does the string read on the Lux side (via the already-defined `STR::strlen` + `UI::xcopy`) and hands Fluxio back raw bytes + a length, the same "Lux does the string work, Fluxio just gets bytes" split the menu bar's own pointer-identity comparison already relies on. The picked path is a *virtual* path relative to the picker's own root (e.g. `/notes.txt`), so `open_picked_file()` prefixes it with `/sys/file` (matching `apps/Quill.lux`'s own `make-vfs-path`) before reusing `load_file()` to actually open it — `scratch_path` became a mutable, dynamically-sized buffer (`scratch_path_len` tracks its real content length) instead of the fixed literal it used to be, so `save_file()` naturally starts targeting wherever was last opened.
&nbsp;&nbsp;&nbsp;&nbsp;**The dialog rendered off-screen.** `SF::show` centers its dialog on `APP::width`/`APP::height`, which only get set by `APP::init`/`sync-canvas` — code Quill.fx's own self-contained loop never runs, so they stayed 0, putting the dialog at large negative coordinates. Caught before it shipped by the very test meant to prove picking works (`test_quill_fx_file_picker_opens_and_picks`, below): it failed to halt at all, because clicks aimed at where the dialog *should* be hit nothing. Fixed by adding `APP::win-set! (w h --)` to `lib/app.lux` (append-only export, index 34) and calling it once at startup with `canvas_size`'s real dimensions.
&nbsp;&nbsp;&nbsp;&nbsp;A real byte-array-size bug surfaced while wiring this up, worth calling out since it's easy to reintroduce: Fluxio's global allocator (Phase 0) packs `byte[N]` globals at exactly `N` bytes with **no alignment padding** between globals — declaring `byte vfs_file_prefix[9] = "/sys/file";`(a literal's declared size must include room for an implicit NUL terminator, so this was already an error at compile time) or, more subtly, any byte array whose size isn't a multiple of 4 shifts every subsequent global's address, misaligning any `int` global declared later and faulting on its very first read/write. Every existing byte-array global in this file happened to already be a multiple of 4; this was the first one that wasn't. Fixed by rounding up to `byte[12]`.
&nbsp;&nbsp;&nbsp;&nbsp;Verified by `test_quill_fx_file_picker_opens_and_picks`: uses `system_set_sandbox_root` (not used by any earlier Quill.fx test) to point the VFS root at an isolated temp directory containing exactly two known files, rather than the real repo root the other tests implicitly run against — makes the picker's directory listing (already alphabetically sorted, `src/vfs.c`'s `create_dir_file`) fully deterministic. Opens the picker, double-clicks the second file (`SF::click-list`'s own double-click-within-500ms rule — a single click only selects), types a marker, saves, and quits: confirms the marker landed in the *newly picked* file and that the *original* scratch file is untouched, proving `save_file()` really re-targeted. Confirmed the test fails (never halts) against the pre-`APP::win-set!` code before trusting it. Also covered by a 1500-frame soak mixing picker open/pick/cancel with hex typing, arrow keys, menu clicks, and random dialog-area clicks, with no fault.
